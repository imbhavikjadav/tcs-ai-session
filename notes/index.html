02

FreightNexus

Agent-built system — Claude Code wrote the whole thing from a 9-file spec. No LLM anywhere in the runtime path. 16 hours, idea to deployed v1.

16 sections
Summary

What it is, and how fast it was built

A pan-India truck tendering marketplace where shippers post shipments and drivers bid — built entirely by Claude Code, no LLM at runtime.

  • 16 hours total build time, idea to deployed MVP.
  • Agentic, spec-driven — Claude Code authored a 9-file spec first.
  • It's a bidding marketplace, not dispatch — shipper picks the best bid, not the first responder.
Who's using it

Four account types, plus an internal Admin

Business Owner, Individual Owner-Driver, Fleet Owner, Fleet Driver — each a genuinely different workflow, not the same form with a label swap.

  • Business Owner: posts shipments, reviews bids, accepts, tracks, confirms payment, rates.
  • Individual Owner-Driver: one login does KYC + truck registration + bidding + execution.
  • Fleet Owner bids centrally, assigns truck+driver after winning; Fleet Driver is invite-only, never bids.
  • Admin is provisioned directly in the DB — no public sign-up path.
Architecture

One Postgres instance, no app server

Next.js talks straight to Supabase Postgres — Row-Level Security enforces access at the database layer itself, not in app code.

  • No dedicated backend — server actions/route handlers hit Supabase directly.
  • Every table is RLS-protected — the database refuses disallowed queries on its own.
  • External services (SendGrid, Google Maps, Vercel Cron) are called directly from Next.js.
Tech stack

What it's actually built from

Next.js 16.3 App Router + Tailwind/shadcn, Supabase (25+ tables), react-hook-form+Zod, Google Maps, react-pdf, Vercel Cron.

  • UI generated via the ui-ux-pro-max skill into a master design system.
  • Storage for KYC docs/photos; Realtime for live GPS during transit.
  • Generated PDF is called "Trip Invoice," deliberately never an E-Way Bill.
Core mechanic

A 14-status state machine runs every trip

Every action is its own visible milestone — new → bid → deposit → transit → delivery → settlement → completed — not a hidden flag.

  • Full chain: new → bid_accepted → deposit paid/confirmed → en route → pickup photos verified → in_transit → arrived → delivery photos verified → final expenses → final payment → completed.
  • Eligibility gates checked server-side and re-checked at bid time: permit, body type, capacity, document validity, verification.
  • Not escrow — payment is bank transfer/UPI off-platform entirely.
The live walkthrough

One real trip, start to finish — TRP00062

A genuine registered shipper (Bhavik) and driver (Akshay) run one real trip end to end, on production data, with real documents.

  • Route: Memnagar (Ahmedabad) → Jewels Circle (Bhavnagar) — 2,800kg electronics, closed container.
  • Settlement: ₹19,000 freight + ₹1,500 allowance + ₹780 actual toll + ₹200 labor = ₹21,480 total.
  • 25% deposit (₹5,312.5) + final payment (₹16,167.5), both confirmed both sides, both rated 5 stars.
Registration + KYC

Nobody skips the review queue

Both accounts (and the truck) go through a genuine multi-step KYC wizard, then sit in a manual admin queue — no auto-approval anywhere.

  • Bhavik: 4-step wizard, Aadhaar uploaded (only last 4 digits stored) → BSOW0057, "Pending Review."
  • Akshay: driver KYC + full truck sub-wizard (details, 5 documents, 4 photos) for GJ01AB1234.
  • Admin queue showed 8 pending items; cleared to 0 after real human review.
Posting → Bidding → Winning

The marketplace mechanic, live

Business owner posts via a 5-step wizard; the trip surfaces only to eligible drivers; Akshay bids, shipper reviews and accepts.

  • Addresses always render as geocoded city/state — never a raw pincode.
  • Bid: ₹19,000 + ₹1,500 allowance + ₹750 est. toll = ₹21,250, status PENDING.
  • On acceptance, a 10-step Trip Actions checklist appears; deposit now due.
Execution

Deposit → pickup → transit → delivery → settlement

Every step needs proof — a bank transfer receipt, pickup photos, a sign-off form — before the trip can move to the next status.

  • Shipper must verify pickup photos as a blocking checkpoint before in-transit.
  • In-transit correctly shows "Signal unavailable" as the honest empty state — no physical GPS tracker connected.
  • Toll trued up (est. ₹750 → actual ₹780) plus a ₹200 loading-labor expense, both with receipts.
Closing out

Two-way confirmation, two real invoices

Final payment needs the driver to see the shipper's proof before confirming — and two separate auto-generated PDF invoices exist for the whole lifecycle.

  • On completion, all 14 milestones turn green and the rating widget appears — both rated 5 stars.
  • Trip Acceptance Invoice generated instantly on bid acceptance.
  • Trip Completion Invoice shows toll true-up, expenses, full status history, and the explicit "not an E-Way Bill" disclaimer.

LegalClear

Runtime AI product — every analysis is a live call to Claude. 7 hours, idea to deployed v1, now on v4 (streaming + caching).

13 sections
Summary

A legal-document translator, live on Claude

Paste or upload a document; Claude streams back a plain-English, risk-flagged breakdown — backed by a real, live API call every time.

  • 7 hours total build time, MVP idea-to-deployed.
  • Built agentically, spec-driven — one scoped version at a time.
  • Live at legalclear.duckdns.org, on AWS EC2 free tier.
Request path

Cache first, then Claude, streamed the whole way

Every request checks a SQLite cache before ever reaching Claude — and Nginx buffering has to be off, or the stream just doesn't reach the browser.

  • Browser → Nginx (proxy_buffering off) → FastAPI → SQLite cache check → Claude on a miss.
  • Cache key: sha256(text), 90-day expiry.
  • SSE sequence: meta → sections → final.
Tech stack

What it's actually built from

React+Vite frontend, FastAPI backend, Anthropic Python SDK (sync + async), SQLite cache, ReportLab PDFs, SendGrid email, all on one EC2 box.

  • Model used for every call: claude-sonnet-4-5.
  • Axios can't stream SSE — native fetch/ReadableStream used instead.
  • Host: AWS EC2 Ubuntu 22.04 t3.micro, behind Nginx.
Build history

Four shipped versions, each scoped and additive

v1 base → v2 streaming → v3 conciseness/UX → v4 caching — each was its own requirements doc fed to Claude Code.

  • v2 had to disable Nginx buffering, or Nginx's default 60s timeout would kill a 5–10 min Claude call.
  • v3 imposed hard word ceilings (verdict: 20 words) — "should I be worried?" answerable in 10 seconds.
  • v4 cache hit = zero token cost, replayed with a deliberate 150ms per-section delay so it still feels like analysis.
Real documents

A genuine lease, analysed live, no mock mode

Every screenshot that follows is from the real production server hitting the real Claude API against a genuine UK tenancy agreement.

  • Document: "AST — 37 Greyfriars Road," a real Assured Shorthold Tenancy.
  • TEST_MODE=false — this is not the app's mock mode.
  • Both the source lease PDF and the 11-page generated report are open for direct preview/download.
The live run

Paste it or upload it, then watch it stream

Streaming begins ~9 seconds in with rotating status text, and section cards mount live as Claude works through all 35 sections.

  • "Powered by Claude AI" badge on the landing page is literally, not just marketingly, true.
  • Progress bar and risk flags appear mid-stream, not after a long wait.
The result

35 sections, tallied risk flags, a real verdict

The finished report extracts 4 parties and tallies 9 HIGH + 20 MEDIUM + 6 NOTE flags — plus email and PDF-download actions afterward.

  • "What to Watch Out For" panel surfaces the top HIGH-severity clauses specifically.
  • Post-analysis: email the report (SendGrid) or download the PDF (ReportLab) — both demoed live.
The $0/month problem

Keeping a free-tier server alive — and controllable from a phone

The 750-hour/month AWS free-tier allowance barely covers continuous uptime, which is why a custom mobile control panel exists.

  • ~730 hrs/month continuous use — almost no margin under the 750-hour cap.
  • DuckDNS + a Netlify maintenance-page fallback if the EC2 instance is stopped.
  • After 12 months: ~$7.50/month indefinitely, or move to Lightsail (~$3.50/mo).
legalclear-control

A pocket-sized on/off switch for a live AWS server

A separate installable web app starts/stops the EC2 instance and repoints DNS from a phone — no laptop needed, no AWS SDK dependency.

  • Hand-rolled AWS SigV4 request signing using only Node's built-in crypto — kept cold-start bundle tiny.
  • AWS credentials live only as Netlify env vars, never in shipped code; repo is private.
  • Installable to a phone home screen like a native app.
04

Claude Integration

A code-level deep dive into exactly how LegalClear talks to Claude. FreightNexus has no equivalent — it never calls the API at runtime.

11 sections
The endpoint

"Calling Claude" is one HTTP POST

Underneath the SDK, it's POST /v1/messages — adding "stream": true is the entire difference between a blocking call and SSE.

  • model: claude-sonnet-4-5 — now a "legacy" model in Anthropic's lineup, but still what this integration calls.
  • max_tokens is a ceiling, not a target — LegalClear sets 8192.
  • system is a separate slot from messages — doesn't count as a conversational turn.
Two clients

Sync and async, same model, both with a 30-min timeout

claude_service.py (sync) and stream_claude_service.py (async) both target the same model, but serve different code paths.

  • Both configure a 30-minute SDK timeout — a large document can genuinely take that long.
  • Hard truncation safeguard is 800,000 characters, not the 50,000 in the env template.
System prompt

Where the actual legal judgment lives

One string carries the entire product's intelligence — 11 numbered rules plus hard word-count ceilings on every field.

  • Rule 7: never soften a harmful clause. Rule 8: always flag arbitration, data-selling, auto-renewal, unilateral modification, liability waivers, jurisdiction.
  • Rule 9: never translate a clause in isolation — cross-reference dependent clauses. This is why chunking a huge doc loses quality.
  • Brevity: verdict ≤20 words, summary ≤25 words, risk explanation ≤15 words.
No memory, ever

Every call starts from zero — no RAG, no embeddings

Each analysis is a cold, single-turn call: fixed system prompt + freshly rebuilt user message, every single time.

  • Why no retrieval: rule 9 needs two far-apart clauses in context simultaneously — similarity search can't guarantee that.
  • Chunking (not retrieval) is the accepted trade-off for documents too large for one call.
Streaming parse

Section-by-section, so there's always something to look at

A 38-section lease takes Claude ~4 minutes — a blank screen that long "reads as broken, not thorough," so results appear from ~10 seconds in.

  • Regex scans a growing buffer for complete <meta>/<section> tags, parses each, then drops consumed text.
  • A heartbeat event on every chunk keeps proxies from timing out mid-stream.
Defensive parsing

Claude doesn't always return clean JSON — plan for it

The non-streaming path strips fences, finds the outer braces, and gets exactly one retry if parsing still fails.

  • Retry primes an assistant turn: "I will now return only the valid JSON object with no additional text:".
  • Distinct exceptions map to distinct failure paths — timeout vs. bad JSON are handled differently.
Chunking

28,000 characters in, because of the 8,192-token ceiling out

Two unrelated units — an empirically tested 28k-character input threshold keeps every output chunk under the 8,192-token cap.

  • Chunk boundaries always prefer a newline, then a space — never a hard mid-word cut.
  • After merging: section IDs renumbered, risk counts recomputed from the real merged data (per-chunk self-counts are unreliable).
  • Party extraction is a separate, smaller call over just the first 120,000 characters.
Cache replay

The instant result still has to feel like analysis

A cache hit replays the exact same SSE event shape as a live run, with a deliberate 150ms delay per section — "instant would read as broken."

  • A dedicated cached event triggers only the "⚡ Instant result" badge — everything else looks identical to a live call.
  • Cache failures are swallowed silently — a cache bug must never cause a user-facing error.
Error handling

Three failure modes, three different messages

API timeout, bad JSON, and a missing API key each get their own message — and the missing-key case deliberately doesn't leak that detail.

  • Missing ANTHROPIC_API_KEY shows the same message as "API unavailable" — never reveals misconfiguration to users.
  • 60-second client heartbeat timeout paired with a 5-second backend ping distinguishes "still thinking" from "connection died."
The real bill

The actual Anthropic Console, live spend and logs

This isn't a hypothetical integration — here's the real account paying for it, with real token counts and real request logs.

  • $23.87 in credits, 91K tokens over the last 7 days, at the time of capture.
  • Logs show individual claude-sonnet-4-5 requests with input/output tokens and streaming flag.

Loop Engineering

Not a product case study — a practical break from typing prompts one at a time toward saved, reusable, self-checking loops.

9 sections
The reframe

Stop prompting Claude. Start looping it.

A prompt runs once and stops. A loop is a small system — trigger, skill, goal, verification, memory — that runs attempt-check-repeat for you.

  • Open with this line: you build the system once, instead of supplying the cycle by hand every message.
The filter

Not every task deserves a loop

Four conditions decide it — fail even one, and a plain one-off prompt is the right tool, not a loop.

  • 1: Does it repeat? 2: Is "done" clearly defined? 3: Can you afford the token cost? 4: Do the tools exist to do the work and check it?
The framework

Every working loop has all four building blocks

Trigger, execution skills, goal+verification, output+memory — this is the mental model the rest of the tab hangs on.

  • Memory is the one almost everybody skips — flag this explicitly.
Triggers

How a loop actually gets started — four real types

Turn-based, /goal, /loop, and /schedule — real Claude Code syntax, not hypothetical.

  • /goal: a separate evaluator checks after each turn — met / impossible / turn-limit-hit.
  • /loop: fixed or self-paced interval, auto-expires after 7 days.
  • /schedule: cloud Routines, no open session needed — triggered by calendar, API, or GitHub event.
Skills

A loop without battle-tested skills just guesses

A skill is a saved Markdown instruction file — it encodes judgment once so every invocation inherits the same standard.

  • Example: pr-review/SKILL.md — 3 explicit rules, must conclude APPROVE/REQUEST CHANGES/COMMENT, never vague.
Goal + verification

A goal with no way to check it is just a hope

The hard part is bridging "abstract" to "verifiable" — especially for subjective, less-quantifiable tasks.

  • For real judgment calls: use two separate agents (one drafts, a different one verifies) — never one agent grading its own work.
Worked example

A live scoreboard, mapped to all four blocks

Every 10 seconds during live matches, re-check the score; only republish if it changed — cheap, verifiable, and needs a cloud trigger.

  • Memory = just the last published score, so an unchanged check costs almost nothing.
Worked example

A /schedule + the skill it actually calls

Every alternate Tuesday morning, audit Production config for "np"/"sandbox" endpoint keywords — a standing safety check, not a release gate.

  • The skill reports the exact offending key + URL — never just a count.
The Ralph technique

The same four blocks, running for hours unattended

A real, Anthropic-published technique — a Stop hook blocks Claude's own exit and re-feeds the same prompt until a completion promise fires.

  • Install: /plugin install ralph-wiggum@claude-code-plugins, then /ralph-loop "..." --completion-promise "complete" --max-iterations 40.
  • Memory = the file system itself — no chat history carries forward each pass, Claude re-reads its own prior work off disk.
  • Raw original version: while true; do cat prompt.md | claude -p; done — no plugin at all.
06

Agents

One layer under Loop Engineering — building a standalone agent callable from your own code, not inside a Claude Code session.

3 sections
The three options

Agent SDK vs. Tool Runner vs. Managed Agents

Same rough shape, three different hosting/control trade-offs — pick based on how much infrastructure you want to own.

  • Agent SDK: Claude Code's full harness, self-hosted, full control.
  • Tool Runner: a lighter loop over your own tools, still self-hosted.
  • Managed Agents: Anthropic hosts the sandbox — best for long-running/scheduled work.
The real example

An on-call agent — and why it can't just be a prompt

It polls an error-rate metric on a timer and only investigates when it spikes — chosen specifically because no chat window is open at 3am.

  • Anchor the whole tab on this line: "couldn't this just be a prompt?" Often yes — the real dividing line is whether a human needs to be present to type the trigger.
  • Code: query() + ClaudeAgentOptions(allowed_tools=[...], permission_mode="acceptEdits") inside a polling while True loop.
Decision guide

Building blocks + picking the right one

Tools, system prompt, permissions, and hooks are the same four concepts from Loop Engineering, just at the level of one agent process.

  • Hooks here are literally the same mechanism as the Ralph Stop hook.
  • Rule of thumb: default to Agent SDK first; only step down or up from there.

Getting started building with AI

Decision tree

Which of these are you actually trying to do?

Three different jobs point to three different tool categories — code-with-help, agent-as-product, or no-code workflow.

  • Coding agents (Claude Code, Codex, Cursor...) vs. Agent frameworks (LangGraph, CrewAI...) vs. No-code (n8n).
The catalog

Three categories, twelve tools

A real, named roundup — not just Claude Code's own ecosystem, competitors included honestly.

  • Codex (OpenAI) is Claude Code's closest direct sibling — same shape, different maker, multi-surface (ChatGPT/IDE/CLI).
  • Cursor: most broadly adopted individually. GitHub Copilot: largest install base overall.
The process

Four steps, in order

Pick one small real task → pick the matching tool category → write a scoped spec first → build in a verification step.

  • Land this line: the four steps are the real leverage, not the fanciest tool.
Where it runs

Local vs. deployed — one deciding question

"Does this need to happen even when my computer is off or asleep?" Yes → deploy it. No → local is simpler and free.

  • LegalClear itself is the "agent inside a deployed app" example — runs 24/7 on EC2.
The closer

AI vs. AGI — a distinction worth getting right

Everything on this whole site is narrow AI. The AI/AGI line is about generality, not intelligence level — and it's a live, unsettled argument right now.

  • Being agentic (loops, hooks, hours of autonomy) isn't the same as being general — say this explicitly, it ties the whole site together.
  • Live case: GPT-6 Astra (OpenAI, Sept 2026) — real ARC-AGI-3 jump ~7.8%→98.6%, OpenAI's own president floated an AGI framing, Nvidia's CEO said AGI arrived.
  • The honest close: real capability jump, but "is this AGI" is genuinely contested — Ethan Mollick's "jagged AGI" framing, and OpenAI's own system card stopped short of claiming it.
