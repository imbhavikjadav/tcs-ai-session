Why these two, side by side

People conflate "built with AI" and "powered by AI" — they're different claims, and this pairing makes the difference concrete. One of these products has Claude in its request path every time a real user hits Submit. The other was built entirely inside Claude Code sessions and never calls an LLM once it's running. Both are legitimate uses of the same underlying model — they just sit on opposite sides of the build-time/run-time line.

LegalClear — Claude at runtime

Every document analysis is a live call to claude-sonnet-4-5. The product's entire value proposition — reading a contract and finding the risk — is the model's output. Take the API key away and the app has nothing left to sell.

Product evolution

Four shipped versions, same running app

Each version was a separate, scoped requirements document fed to Claude Code with an explicit "do not rebuild, only add this" instruction — a deliberate discipline that kept a single-session build from regressing earlier work.

v1
Base build
Paste or upload a document, one blocking request, one complete JSON response rendered all at once. Simple, but a 5–10 minute Claude call on a large document meant a blank loading screen — and Nginx's default 60s proxy_read_timeout would kill the connection long before Claude finished.
v2
Streaming
Added a second endpoint, /api/translate-stream, that asks Claude to emit XML-tag-delimited JSON fragments (<meta>, <section>, <final>) instead of one blob, and forwards each as a Server-Sent Event the moment it's complete. First results now appear in 5–10 seconds regardless of document size. Required disabling Nginx's response buffering — see the Claude Integration tab for exactly why.
v3
Conciseness & UX redesign
The first two versions let Claude write as much as it wanted per field — summaries ran to paragraphs, risk explanations rambled. v3 added hard word-count ceilings to the prompt (verdict: 20 words, risk explanation: 15 words) and redesigned the results page around a single question: "should I be worried about this document?", answerable in the first 10 seconds without scrolling.
v4
Hash-based caching
Every submission still called Claude, even for a document someone else had already translated. v4 added a SQLite cache keyed on a normalised SHA-256 hash of the document text — a cache hit replays the stored result through the same streaming interface with a 150ms per-section delay (so it still feels like analysis, not a suspicious instant response) and shows a "⚡ Instant result" badge. Zero token cost on a hit.

FreightNexus

A pan-India, mobile-first truck tendering marketplace. Not a dispatch app — a bidding marketplace: a shipper posts a shipment, eligible verified drivers bid on it with an itemised price, and the shipper picks the bid that suits them, not just the first one that shows up. Data model, in brief

The state machine that runs every trip

A trip moves through 14 explicit statuses from posting to completion — not because the domain needs 14 states, but because every action either side takes (confirm the deposit, verify pickup photos, approve the final amount) is deliberately its own resting state so it shows as its own row on both parties' status timeline, rather than an invisible background flag.

trips.status — real forward ordersrc/lib/trips/milestones.ts
new → bid_accepted → deposit_pending_payment → deposit_pending_confirmation
→ en_route_to_pickup → pickup_photos_pending_verification → in_transit
→ arrived_pending_signoff → delivery_photos_pending_verification
→ final_expenses_pending_submission → final_amount_pending_approval
→ final_payment_pending_payment → final_payment_pending_confirmation → completed

branches:  cancelled  (from `new` through pickup, penalty rules depend on stage)
           expired    (zero bids after 2 days, auto-transitioned by Vercel Cron)
Eligibility filtering isn't cosmetic. When a trip posts, the set of drivers who even get notified is computed server-side against five gates: national permit vs. home-state match, truck body type vs. goods nature, capacity vs. weight, document validity, and verification status. The same filter re-runs at bid-submission time — a truck's documents could have expired in the gap between the notification email and the bid attempt.
Not an escrow service, and the product says so everywhere. The platform never custodies funds — payment is bank transfer/UPI, entirely off-platform, with proof-of-payment upload and two-way confirmation as the only tracking layer. The generated PDF is explicitly a "Trip Invoice / Shipment Summary," never an E-Way Bill — that's a legally defined GST document requiring a registered business entity the platform operator doesn't have.

How LegalClear actually talks to Claude

This is the one part of the site written for people who read code, not just screenshots. 1 · Model & client setup

Two clients, two endpoints, one model

LegalClear runs two separate integration paths against the same model, claude-sonnet-4-5 — a synchronous batch path (claude_service.py) and an async streaming path (stream_claude_service.py). Both exist because the streaming path was added in v2 without touching the original — the batch endpoint is kept as a fallback and for the large-document chunking pipeline, which doesn't stream sub-chunks individually.

backend/services/claude_service.pysync client, 30-min timeout
def _create_claude_client(api_key: str):
    sdk_timeout = anthropic.Timeout(
        timeout=1800.0,   # 30 minutes — matches the longest realistic document
        connect=30.0,
        read=1800.0,
        write=60.0,
        pool=10.0,
    )
    return anthropic.Anthropic(api_key=api_key, timeout=sdk_timeout)
backend/services/stream_claude_service.pyasync client, same timeout budget
def _create_async_claude_client(api_key: str):
    return anthropic.AsyncAnthropic(
        api_key=api_key,
        timeout=anthropic.Timeout(timeout=1800.0, connect=30.0, read=1800.0, write=60.0, pool=10.0),
    )

A 30-minute SDK timeout looks extreme until you remember it has to survive worst case: MAX_DOCUMENT_CHARS defaults to 50,000 in the env template, but the actual safeguard in code is 800,000 characters (_MAX_DOCUMENT_CHARS) before hard truncation — a genuinely huge contract, chunked into ~28 pieces, each needing its own full model round-trip.

2 · The system prompt

Where the actual legal judgment lives

This is the entire product's intelligence, in one string. It does three jobs at once: sets the analytical stance (assume unfair terms until proven otherwise), fixes an output contract strict enough to parse reliably, and — added in v3 — caps every field's length so the result reads as a verdict, not an essay.

SYSTEM_PROMPT (streaming variant, abridged)stream_claude_service.py:49
You are LegalClear, an expert legal document analyser.

Your role is to translate legal documents into plain English and identify risks
for the person being asked to agree to the document (referred to as "the user").

CRITICAL STREAMING INSTRUCTION:
You must output your analysis section by section.
For each section you find, output a complete JSON object on its own line,
wrapped in <section> tags like this:

<section>{"section_id": 1, "title": "...", "category": "...",
  "original_excerpt": "...", "plain_english": "...",
  "risk_flags": [{"severity": "HIGH", "title": "...", "explanation": "..."}]}</section>

Before the first section, output document metadata wrapped in <meta> tags:
<meta>{"document_name": "...", "verdict": "...", "parties": [...], "summary": "..."}</meta>

After ALL sections, output a final summary wrapped in <final> tags:
<final>{"overall_risk_level": "LOW|MEDIUM|HIGH", ...}</final>

RULES:
1.  Read the ENTIRE document before outputting anything
2.  Output <meta> first, then each <section>, then <final>
3.  Every section JSON must be complete and valid — never break a section across lines
5.  Categorise every clause: Your Rights | Company Rights | Your Obligations |
    Company Obligations | Termination | Liability & Disputes | Data & Privacy |
    Payment & Fees | Intellectual Property | Other
7.  Never soften language around genuinely harmful clauses
8.  Always flag: arbitration, data selling, auto-renewal, unilateral modification,
    liability waivers, jurisdiction clauses
9.  Cross-reference dependent clauses — never translate one in isolation if it
    depends on or is modified by another
11. Approach every document with the assumption it may contain unfair terms

OUTPUT BREVITY RULES — strict, followed exactly:
- verdict: EXACTLY 1 sentence, max 20 words. The single most important thing
  the user needs to know. Direct and honest.
- summary: EXACTLY 1 sentence, max 25 words. No risk language — just scope.
- plain_english (per section): Max 3 sentences. What it does, who it affects,
  the practical implication. No padding.
- risk flag explanation: Max 15 words. Be direct. No padding or softening.
Rule 9 is the one that actually needs a large-context model. "Never translate a clause in isolation if it depends on or is modified by another" is only enforceable if the model can see the whole document at once — which is exactly why chunked analysis (below) loses quality on very large documents and why the chunk boundary logic tries hard to overlap on paragraph breaks rather than mid-clause.
3 · Building the request

User message = instructions + schema + the actual document

The user turn is a template, not free text — it restates the exact JSON shape expected, field by field, immediately followed by the raw document text. Repeating the schema in the user message (on top of the system prompt) measurably improves adherence on long documents, where the system prompt's instructions are further back in the context window by the time generation starts.

4 · The streaming protocol

Why XML tags around JSON, not JSON alone

A single top-level JSON object can't be usefully parsed until the closing brace arrives — you can't safely render "the first two sections" out of a half-finished blob. The fix: ask Claude to wrap each independent unit in a plain-text tag pair, and scan the growing text buffer for complete <tag>...</tag> pairs on every chunk, parsing and emitting each one the instant it closes.

The extraction loopstream_claude_service.py:150
buffer = ""
async with client.messages.stream(
    model="claude-sonnet-4-5", max_tokens=8192,
    system=SYSTEM_PROMPT, messages=[{"role": "user", "content": user_message}]
) as stream:
    async for text_chunk in stream.text_stream:
        buffer += text_chunk

        # extract a complete <meta> block the moment it closes
        meta_match = re.search(r'<meta>(.*?)</meta>', buffer, re.DOTALL)
        if meta_match:
            meta_data = json.loads(meta_match.group(1).strip())
            yield {"type": "meta", "data": meta_data}
            buffer = buffer[meta_match.end():]   # drop consumed text

        # drain every complete <section> block in this chunk (there may be >1)
        while True:
            section_match = re.search(r'<section>(.*?)</section>', buffer, re.DOTALL)
            if not section_match: break
            section_data = json.loads(section_match.group(1).strip())
            yield {"type": "section", "data": section_data}
            buffer = buffer[section_match.end():]

        yield {"type": "heartbeat", "data": {}}   # every chunk, keeps proxies alive

The <final> block is extracted once after the stream ends, since it's the model's summary of everything it just wrote — it can only be correct once every section exists.

5 · Parsing the non-streaming path

Claude doesn't always return clean JSON — plan for it

The batch endpoint asks for a single JSON object with no markdown fences, no preamble. It usually complies. "Usually" is not a production error-handling strategy, so every response goes through a defensive extractor before json.loads ever sees it.

_extract_json — strips fences, finds the outermost bracesclaude_service.py:109
def _extract_json(text: str) -> dict:
    text = text.strip()
    # strip ```json ... ``` fences anywhere in the text, even mid-string
    text = re.sub(r"```(?:json)?", "", text)
    text = text.strip()
    # find the OUTERMOST { ... } — robust to any preamble/postamble Claude adds
    start = text.find("{")
    end = text.rfind("}")
    if start != -1 and end != -1 and end > start:
        text = text[start : end + 1]
    return json.loads(text)

If that still fails to parse, there's exactly one retry — not a loop, a single deliberate second attempt with the model's own (empty) turn primed to bias it toward compliance:

The one-shot retryclaude_service.py:398
try:
    extra = [{"role": "assistant",
               "content": "I will now return only the valid JSON object with no additional text:"}]
    raw = _call(extra_messages=extra)   # same user message, one extra primed turn
    return _extract_json(raw)
except (APITimeoutError, APIConnectionError, APIStatusError):
    raise RuntimeError(_CLAUDE_API_ERROR_MESSAGE)
except Exception:
    raise RuntimeError(_CLAUDE_PARSE_ERROR_MESSAGE)

Pre-filling an assistant turn with the start of the desired response is a real Anthropic API technique for steering output format — here it's used defensively, only on retry, rather than on every call, since it costs an extra round trip and the first attempt succeeds the overwhelming majority of the time.

6 · Large documents — chunking

What happens past ~28,000 characters

Claude's own context window could handle far more text than this in one call — the chunk size here is chosen to keep each individual analysis pass fast and its output comfortably under the 8,192-token output ceiling, not because the model runs out of room to read.

ConstantValueWhy
_MAX_OUTPUT_TOKENS8192Model's real output ceiling — a chunk's analysis must fit inside one response.
_MAX_CHUNK_CHARS28,000Split threshold — documents under this go through the single-call path.
_CHUNK_OVERLAP_CHARS2,000Each chunk after the first re-includes its predecessor's tail, so a clause split across the boundary still has context on both sides.
_MAX_DOCUMENT_CHARS800,000Hard safeguard — beyond this the document is truncated rather than chunked indefinitely.

Chunk boundaries prefer a newline, then a space, over a hard character cut — text.rfind("\n", start, end) before falling back to text.rfind(" ", start, end) — so a split never lands mid-word or, ideally, mid-sentence. Each chunk is analysed independently, section IDs are renumbered sequentially after merging, and — deliberately — the merged risk counts are recomputed from the actual merged risk_flags arrays rather than trusted from each chunk's self-reported count, because per-chunk counts from the model are "approximate or inconsistent across chunks," per the code's own comment. Party extraction runs as a separate, smaller call over the first 120,000 characters, since parties are usually named early and a full second pass isn't needed.

7 · Caching — replaying a stream that never called Claude

The instant result has to still feel like analysis

The cache key is a SHA-256 hash of the document text after whitespace and case normalisation, so "the same NDA with different line endings" still hits. The interesting part is what happens on a hit — the frontend has no separate "cached result" code path, so the backend has to replay the stored result through the exact same SSE shape a live call would produce.

Cache-hit replay — same chunk order, deliberate delaycache flow, translate.py
meta_chunk = {"type": "meta", "data": {...}}
yield f"data: {json.dumps(meta_chunk)}\n\n"
await asyncio.sleep(0.15)   # 150ms — instant would read as broken, not fast

for section in cached_result["sections"]:
    yield f"data: {json.dumps({'type': 'section', 'data': section})}\n\n"
    await asyncio.sleep(0.15)

# ...final chunk, then a dedicated 'cached' event the frontend uses only to
# show the ⚡ Instant result badge — everything else is indistinguishable from live
yield f"data: {json.dumps({'type': 'cached', 'data': {'is_cached': True}})}\n\n"
The 150ms isn't a technicality — it's a UX decision written directly into backend code. A cache hit that returned everything in one network frame would look like a bug to a user who just watched the exact same tool take 45 seconds on the previous document. Pacing the replay to feel "fast, not instant" was worth encoding as a constant rather than leaving to chance.

Resilience is explicit throughout: the cache write after a live call is wrapped in its own try/except with a comment stating a cache failure "must never cause a user-facing error," and a cached result missing any of document_name / sections / overall_risk_level is treated as a miss and silently falls through to a real Claude call rather than replaying something broken.

On the streaming path specifically, a 60-second client-side heartbeat timeout (paired with the backend's own 5-second ping events) distinguishes "Claude is still thinking" from "the connection actually died" — if 60 seconds pass with zero bytes, even pings, the frontend gives up and shows a timeout message rather than a silently frozen progress bar.

Infrastructure & operations

Keeping a $0/month server alive — and controllable from a phone

LegalClear runs on a single AWS EC2 t3.micro instance inside the AWS Free Tier's 750-hour/month allowance. That allowance is per account, not per instance, and free only for the first 12 months — which shapes almost every operational decision below, right down to a purpose-built mobile control panel whose entire job is turning the server off when nobody's using it.

The streaming-vs-proxy problem

Why a working backend still showed a blank screen

This is the single most instructive bug in the whole deployment. The streaming feature (v2, see Claude Integration tab) worked perfectly in local dev and then did nothing visible in production — no error, just a blank screen until the entire response was ready, exactly the behaviour streaming was built to eliminate.

1
Nginx buffers proxied responses by default
Its default behaviour is to read the entire upstream response into a buffer before sending any of it to the browser — exactly the "wait for everything, then show it all" pattern the streaming feature was built to replace. FastAPI was sending bytes the instant Claude produced them; Nginx was silently holding every one of those bytes until the connection closed.
2
The fix — three directives, none optional
proxy_buffering off; stops Nginx accumulating the response. proxy_set_header X-Accel-Buffering no; is a second, belt-and-braces instruction some Nginx configurations respect even when the first is missed. chunked_transfer_encoding on; ensures each SSE event is forwarded as its own chunk rather than concatenated.
3
Generous, explicit timeouts
proxy_read_timeout 300s (raised from Nginx's 60-second default) buys enough headroom for a real Claude call, on top of the 5-second heartbeat pings the backend sends specifically to keep the connection looking "alive" to any proxy watching for silence.
/etc/nginx/sites-available/legalclear — the /api/ blockproduction config
location /api/ {
    proxy_pass http://127.0.0.1:8000;
    proxy_http_version 1.1;

    # the three lines that actually make streaming work
    proxy_buffering off;
    proxy_cache off;
    proxy_set_header X-Accel-Buffering no;

    proxy_set_header Connection '';
    chunked_transfer_encoding on;

    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    proxy_connect_timeout 300s;
    proxy_send_timeout 300s;
    proxy_read_timeout 300s;
    send_timeout 300s;
}
The lesson generalises past Nginx. AWS's Application Load Balancer has its own 60-second idle timeout with the same failure mode, and any CDN or reverse proxy in front of an SSE endpoint needs the equivalent of these three directives. "It works locally" tells you nothing about whether anything sitting between the backend and the browser in production also needs to be told not to buffer.

The problem free-tier billing creates

750 hours a month means the server can't just stay on forever

A single EC2 instance running continuously uses roughly 730 hours a month — inside the 750-hour allowance, but with almost no margin, and only for the account's first 12 months. After that it's roughly $7.50/month indefinitely. Two options followed from this: stop the instance during genuinely idle periods (stopping pauses the hour counter entirely; only terminating loses data), or accept the eventual small monthly cost. The operational tooling below exists to make the first option practical without needing a laptop.

legalclear-control

A phone-sized on/off switch for a real AWS server

A second, separate, private repository — deliberately never merged into the main LegalClear codebase — containing a single-page mobile web app that starts and stops the EC2 instance and repoints DNS accordingly, with no laptop, terminal, or AWS Console required. Installable to a phone home screen like a native app.

What it does

▶
Start Server
Calls EC2's StartInstances, polls for up to 90 seconds until AWS assigns a fresh public IP (start-up is asynchronous — there's no instant answer), then pushes that IP to DuckDNS. The domain goes live the moment DNS propagates.
■
Stop Server
Repoints DuckDNS at the Netlify maintenance site first, then calls StopInstances — deliberately in that order, so visitors see a branded "back soon" page instead of a connection-refused error during the stop.
↻
Check Status
Calls DescribeInstances and renders a live badge — running (pulsing green), stopped (red), or checking (blue) — plus the current public IP.

How it's built

A static HTML/CSS/JS page (no framework — the whole UI is one index.html) deployed to Netlify, backed by one Netlify serverless function, netlify/functions/control.js. That function does the actual work: it hand-implements AWS Signature Version 4 — HMAC-SHA256 request signing — in plain Node.js using only the built-in crypto module, calling the raw EC2 HTTP API directly rather than pulling in the full AWS SDK, which would be considerable weight for three actions. Password gate is a client-side session check; the real security boundary is that AWS credentials live only as Netlify environment variables, never in the shipped code, and the repository itself is private.

netlify/functions/control.js — the signing corehand-rolled SigV4, no AWS SDK dependency
function getSignatureKey(key, dateStamp, regionName, serviceName) {
    const kDate    = hmac('AWS4' + key, dateStamp);
    const kRegion  = hmac(kDate, regionName);
    const kService = hmac(kRegion, serviceName);
    return hmac(kService, 'aws4_request');
}

Why hand-roll SigV4 instead of installing aws-sdk? A Netlify Function has a cold-start cost proportional to its bundle size, and this function needs exactly three EC2 read/write calls. Signing a request by hand in ~40 lines against Node's built-in crypto keeps the whole function dependency-free — nothing to npm install, nothing to go stale.
